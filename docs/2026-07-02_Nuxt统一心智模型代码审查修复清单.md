## P0：优先修复

### ✅ P0-1 收紧 API 请求目标与 Token 注入边界（完成）

- **根因**：`useApi()` 只用 `new URL(url, API_URL_PARSE_BASE).pathname` 判断公共路径，但最终把原始 `url` 交给 `$fetch`；当调用方传入绝对外部 URL 且路径不是 public endpoint 时，会继续注入 `Authorization`。
- **影响**：Bearer access token 可能被发送到非预期 origin，是当前最高优先级的安全边界问题。
- **前置条件**：存在可传入绝对 URL 的调用路径，或后续业务代码复用 `useApi().request()` 请求第三方地址。
- **修复方案**：新增 `resolveApiRequest()`，统一解析 `baseURL + url` 的最终 origin；默认拒绝非相对 URL / 非配置 API origin 的 authenticated 请求。只有相对路径或与 `runtimeConfig.public.apiBaseURL` 同 origin 的请求可注入 token；显式 public 请求也不应携带 token。补测试覆盖“外部绝对 URL 不带 Authorization / 直接拒绝”。
- **涉及文件**：`app/composables/useApi.ts`、`app/types/api.ts`、`tests/nuxt/use-api.spec.ts`。
- **本轮复核状态**：已抽出 `resolveApiRequest()`，请求 origin、public 策略与 Authorization 注入边界已由 `tests/nuxt/use-api.spec.ts` 覆盖；完整 `pnpm release:check` 已通过。

### ✅ P0-2 重构 RBAC：Admin Boundary 必须独立 All 校验

- **根因**：`authStore.can()` 把 `adminBoundaryPolicy` 派生的角色/scope 与页面自定义角色/scope 合并后，再统一套 `permissionMode`。如果某页面使用 `PermissionMode.Any`，就可能用额外 scope 稀释 `BusinessAdmin` / `OpsOnly` 的边界要求。
- **影响**：后台业务边界和运维边界可能被配置项绕松，权限模型心智不稳定。
- **前置条件**：任意页面、导航项或动作配置了 `adminBoundaryPolicy` 且同时配置 `permissionMode: Any`。
- **修复方案**：把 `can()` 拆成两段：先对 `adminBoundaryPolicy` 永远按 `PermissionMode.All` 校验；通过后再对页面自定义 `requiredRoles/requiredScopes` 使用页面自己的 `permissionMode`。增加负测：`BusinessAdmin + PermissionMode.Any + 额外 scope` 不能绕过 `AuthRead`。
- **涉及文件**：`app/stores/auth.ts`、`app/types/auth.ts`、`tests/nuxt/auth-rbac.spec.ts`、`tests/nuxt/route-middleware.spec.ts`。
- **本轮复核状态**：源码已按 Admin Boundary 独立 All 校验实现，`PermissionMode.Any` 不能稀释 `BusinessAdmin` / `OpsOnly` 边界，定向 RBAC 与 route middleware 测试通过。

### ✅ P0-3 修复 Refresh 状态机的重入与错误重放

- **根因**：`runRefresh()` 成功刷新 token 后调用 `fetchMe()`，而 `fetchMe()` 走 `createAuthClient().me()`，底层仍会经过 authenticated API refresh 逻辑；同时 `refresh()` 无可用 refresh token 时只清 session 并返回，`useAuthenticatedApi()` 随后仍可能重放原请求。
- **影响**：可能出现等待自己的 refresh lock、刷新失败后仍重放、或 session 已清空但请求继续发出的状态机漏洞。
- **前置条件**：`/auth/me` 在 refresh 过程中返回 401/token expired，或 refresh token 过期/缺失后触发 authenticated 请求重放。
- **修复方案**：让 `refresh()` 返回明确结果（例如 `boolean` 或 token issue），无可用 refresh token 时抛标准化认证错误；`runRefresh()` 内部的 `fetchMe` 使用 `skipRefresh` 或 raw authenticated call；重放原请求前必须确认 access token 存在、sessionVersion 未失效、refresh 已成功。
- **涉及文件**：`app/stores/auth.ts`、`app/composables/useAuthenticatedApi.ts`、`app/services/api/auth.ts`、`tests/nuxt/auth-session.spec.ts`。
- **本轮复核状态**：已接入 refresh lock、`skipRefresh`、无 refresh token 标准错误、access token 存在校验与 `sessionVersion` 失效保护；`tests/nuxt/auth-session.spec.ts` 已补充 refresh 期间会话切换不得重放原请求的直接负测，完整 `pnpm release:check` 已通过。

### ✅ P0-4 统一 Envelope 成功/失败与契约错误模型

- **根因**：`unwrapResponseEnvelope()` 只要识别出 response envelope 就直接返回 `data`，未校验 `header.code` 是否为成功；`unwrapAdminEnvelope()` 的契约错误直接 `throw new Error()`，不会进入统一 `ApiErrorPayload`；admin schema 只检查存在，不检查期望版本。
- **影响**：后端返回 fault envelope 时可能被当成功数据继续传递；admin contract error 与请求错误展示、session 消费、页面错误提示不一致。
- **前置条件**：后端返回 `header.code !== success` 的 envelope，或 admin 接口返回 kind/operation/schema_version 不匹配。
- **修复方案**：建立单一 envelope parser：外层 envelope 必须校验 success code；fault envelope、contract mismatch、schema mismatch 都转换成稳定 `ApiErrorPayload`。`AdminEnvelopeValidationOptions` 增加 `expectedSchemaVersion`，所有 admin client 传入模块 schema version。测试覆盖 fault envelope、schema mismatch、kind mismatch、operation mismatch 都走统一错误。
- **涉及文件**：`app/services/api/envelope.ts`、`app/types/api.ts`、`app/services/api/admin.ts`、`app/utils/errors.ts`、`tests/nuxt/admin-api.spec.ts`、`tests/unit/errors.test.ts`。
- **本轮复核状态**：源码已校验 `header.code` 并统一契约错误；已补 HTTP 200 resolved fault envelope 直接负测，验证 `unwrapResponseEnvelope()` 抛出稳定 `ApiErrorPayload`，完整 `pnpm release:check` 已通过。

### ✅ P0-5 明确 Refresh Token 生产持久化方案（文档化完成，BFF/httpOnly 未落地）

- **根因**：当前直连 Bearer 模式把 `accessToken` 与 `refreshToken` 写入普通 `useCookie()`，cookie 可被 JS 读取，无法设置 `httpOnly`。
- **影响**：一旦发生 XSS，refresh token 可被直接窃取；这不是开发期小问题，而是生产鉴权架构决策。
- **前置条件**：生产仍采用浏览器直连 API，并持久化 refresh token。
- **修复方案**：最佳方案是改 Nuxt BFF / 后端 httpOnly same-site session，把 refresh token 留在服务端或 httpOnly cookie。若短期必须直连 API，应在 README 和安全规格中明确接受风险，并至少缩短 refresh token 生命周期、限制作用域、完善 CSP；不要把它包装成“安全已完成”。
- **涉及文件**：`app/stores/auth.ts`、`README.md`、`.env.example`、`docs/nuxt应用骨架规格.md`。
- **本轮复核状态**：README 与 `docs/nuxt应用骨架规格.md` 已同步生产首选 Nuxt BFF / 后端 httpOnly same-site session；直连 Bearer refresh token 已标记为显式生产风险。

- **修复方案**：在 `createAdminOpsClient().logs.securityEvents()` 内归一化为单一 canonical 字段，页面只消费一个字段；类型层收紧。如果必须兼容旧后端，把兼容逻辑留在服务层并加测试。
- **涉及文件**：`app/types/admin-ops.ts`、`app/services/api/admin.ts`、`app/pages/admin/ops/logs.vue`、`tests/nuxt/admin-api.spec.ts`。
- **本轮复核状态**：已完成。`AdminSecurityEventListPayload` 类型和页面只消费 canonical `events` 字段；legacy `records` 兼容仅保留在 `createAdminOpsClient().logs.securityEvents()` 服务层内，并由 `tests/nuxt/admin-api.spec.ts` 覆盖 `records -> events` 归一化且不向页面泄露 `records`。

### ✅ P1-7 修复 SSR Runtime Error 旧 handler 吞错

- **根因**：`runtime-errors.server.ts` 调用 `previousErrorHandler` 后，只要旧 handler 存在就 `return`，未知 SSR Vue 错误不会升级为统一 fatal error。
- **影响**：和文档声明的“服务端未知错误升级”不一致；生产中若 Nuxt 或其他插件先注册 handler，当前插件会失效。
- **前置条件**：服务端已有 `vueApp.config.errorHandler`，并出现非 HTTP status error。
- **修复方案**：旧 handler 仍调用，但不能作为“已处理”依据；只对已知 HTTP error 跳过升级。补测试：存在旧 handler 时，unknown error 仍会被 `createError({ fatal: true })` 升级。
- **涉及文件**：`app/plugins/runtime-errors.server.ts`、`tests/nuxt/runtime-errors.spec.ts`。
- **本轮复核状态**：源码与 runtime error 用例均已通过 P1 定向门禁；`vitest.config.ts` 已提高 Nuxt 项目 hook/test timeout，完整 `pnpm release:check` 已通过。

### ✅ P1-8 E2E 不应在 CI 复用未知本地服务

- **根因**：`playwright.config.ts` 中 `reuseExistingServer: true` 对所有环境生效。
- **影响**：CI 或共享机器上如果 `127.0.0.1:3000` 已有旧服务，E2E 可能测到错误应用，产生假阳性或假阴性。
- **前置条件**：默认端口已有进程，且未显式设置 `NUXT_TEST_HOST`。
- **修复方案**：改为 `reuseExistingServer: !process.env.CI`；CI 使用独占端口或端口冲突即失败。本地保留复用以提高开发效率。
- **涉及文件**：`playwright.config.ts`、`README.md`、`tests/e2e/smoke.spec.ts`。
- **本轮复核状态**：`playwright.config.ts` 已使用 `reuseExistingServer: !process.env.CI` 且默认端口为 `3310`；README、`docs/nuxt应用骨架规格.md` 与历史执行方案已同步 `http://127.0.0.1:3310`、`NUXT_TEST_HOST` 与 CI 不复用未知本地服务口径。当前未发现 `.github/workflows`，CI 说明仅代表 Playwright 配置在 `CI` 环境变量下不复用未知服务，不代表 CI 流水线已接入。
