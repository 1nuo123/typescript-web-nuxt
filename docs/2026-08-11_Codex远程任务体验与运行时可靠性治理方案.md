# 2026-08-11 Codex 远程任务体验与运行时可靠性治理方案

## 1. 文档目的

本文针对 Codex 远程任务在审批、实时事件、认证恢复、Diff 渲染、任务状态、滚动定位、元数据恢复、响应式布局和可观测性方面暴露的 16 个问题，基于当前前后端实际代码给出根因、最佳实践方案、实施清单、测试要求和部署验收标准。

适用代码库：

- 前端：`E:\python_web_fastapi\typescript-web-nuxt`
- 后端：`E:\python_web_fastapi\work`
- 后端编码规范：`E:\python_web_fastapi\work\docs\standard`
- 统一入口：`http://localhost:8080`

本文不把界面上的兜底文案视为根因修复。所有方案优先在数据契约、事务边界、状态机、协议能力和可观测性边界解决问题，组件级降级只承担最后一道隔离责任。

## 2. 当前架构与故障传播链

当前主链路如下：

1. Nuxt 浏览器端通过 REST 获取主机、工作区、线程、审批和认证快照。
2. Caddy 在 `8080` 端口统一反向代理 Nuxt 与 FastAPI。
3. FastAPI 使用 PostgreSQL 保存线程索引、操作、审批审计等权威状态，使用 Redis 承担实时流、控制信号和在线状态能力。
4. Windows Agent 通过 WSS 连接 FastAPI 控制面，并与本机 Codex App Server 通信。
5. Agent 将 App Server 通知和审批请求映射为稳定的产品事件，再由 FastAPI 发布给浏览器。
6. Nuxt 对 REST 快照和实时事件做规范化后写入 Pinia 投影，页面只消费投影数据。

故障会沿以下边界传播：

- App Server 字段不完整 -> Agent 映射不完整 -> FastAPI 发布部分对象 -> 前端覆盖完整快照 -> 排序或渲染崩溃。
- REST 与实时事件使用不同校验路径 -> 相同实体在不同入口得到不同形态 -> Reducer 和组件出现不可预测分支。
- 全局错误处理把普通异步异常升级为 fatal -> 一个审批请求失败导致整页不可用。
- 代理路径同时承担页面和 API -> 新标签页或硬刷新请求被转发到后端 API -> 浏览器直接显示 401 JSON。

## 3. 治理原则

### 3.1 契约优先

- 外部输入必须在 API、Agent 协议和浏览器实时事件边界完成结构化校验。
- 判别字段与对应正文必须原子出现，例如 `kind=diff` 时 `diff` 不允许为 `null`。
- REST 快照和实时事件必须复用同一规范化器。
- 缺失字段只能使用确定性默认值，不允许依赖当前时间制造排序抖动。

### 3.2 单一状态机

- 页面顶部、消息区、导航角标、审批卡片使用同一个状态 selector。
- 状态必须区分 `submitting`、`accepted`、`starting`、`running`、`waiting_approval`、`stalled` 和终态。
- operation ID、trace ID 等诊断字段不参与普通用户状态表达。

### 3.3 局部隔离

- 单个时间线条目渲染失败时只隔离该条目。
- 普通 Promise 拒绝和窗口事件只记录诊断，不应自动替换整个页面。
- 只有未被组件边界接住的根级渲染错误才进入 fatal 错误页。

### 3.4 权威状态与最终一致性

- PostgreSQL 快照是审批和线程索引的权威状态。
- 实时事件用于低延迟投影，不允许发布比 REST 更弱的对象。
- 外部 Agent/App Server 调用无法加入数据库原子事务时，必须通过幂等键、版本、结果对象、outbox、补偿和重新同步表达最终一致性。

## 4. 问题一：审批页稳定崩溃

### 4.1 实际根因

`approval.opened` 曾直接发布 Agent 上报的部分审批对象，其中缺少 `owner_subject_id`、`created_at`、`updated_at` 等 REST 对象具备的字段。前端收到事件后用部分对象覆盖完整对象，审批排序调用 `localeCompare` 时读取到 `undefined`。

相关代码：

- 后端：`src/infrastructure/codex/codex_control_runtime.py`
- 后端契约：`src/core/codex_contract/approval_contract.py`
- 前端规范化：`app/utils/codex-contract-normalizer.ts`
- 前端 Store：`app/stores/codex-approvals.ts`

### 4.2 最佳实践方案

- 后端持久化审批后，实时事件必须重新读取完整的权威审批快照并发布。
- 前端在实时边界深度规范化审批对象。
- 所有日期字段提供固定纪元默认值，排序增加审批 ID 作为稳定次序。
- Store 使用 `version + updated_at` 拒绝乱序旧事件。

- [x] Store 拒绝较低版本和较旧时间戳事件。

### 4.4 验收标准

- 审批对象缺少可选字段时页面不崩溃。
- 缺少审批 ID、主机 ID 或线程 ID 时事件被拒绝，不进入 Store。
- 旧版本事件不能把已完成审批恢复为待审批。
- 相同时间戳的审批排序在刷新前后保持一致。

## 5. 问题二：大型 Diff 导致会话页崩溃

### 5.1 实际根因

前端实时校验只检查顶层对象，允许 `kind=diff` 但 `diff=null` 或嵌套 `files/hunks/lines` 非法的数据进入 Reducer。后端时间线契约也曾允许 Diff 判别字段与正文不一致。大型 Diff 同时一次性渲染大量 DOM 节点，放大了错误和性能风险。

相关代码：

- 后端契约：`src/core/codex_contract/thread_contract.py`
- 前端规范化：`app/utils/codex-contract-normalizer.ts`
- 前端校验：`app/utils/codex-event-validator.ts`
- Diff 组件：`app/components/codex/CodexDiffView.vue`
- 条目边界：`app/components/codex/CodexTimelineItemBoundary.vue`

### 5.2 最佳实践方案

- 后端使用判别变体校验，Diff 正文缺失时拒绝跨越 API 边界。
- 前端对文件、hunk、line 做深度规范化。
- Reducer 每次原子替换完整 Diff，不拼接半成品嵌套结构。
- 大型 Diff 首屏只渲染固定行数，用户按块继续加载。
- 每个时间线条目设置独立错误边界并记录 thread、turn、item 上下文。

### 5.3 任务清单

- [x] 后端拒绝 `kind=diff, diff=None`。
- [x] 前端拒绝嵌套 `null` Diff。
- [x] REST 快照与实时事件复用时间线规范化器。
- [x] 大型 Diff 采用 800 行分块渲染。
- [x] 空 Diff 显示稳定空状态。
- [x] 每条时间线内容使用独立 Nuxt 错误边界。
- [x] 增加空 Diff、非法 Diff 和 805 行分块渲染测试。
- [ ] 当单文件达到数万行时升级为真正虚拟列表，而不是继续累积已加载 DOM。
- [ ] 后端分页接口支持按文件和 hunk 游标读取超大 Diff。
- [ ] 为 Diff 解析耗时、节点数和渲染耗时增加性能指标。

### 5.4 验收标准

- 非法 Diff 被记录为契约错误，页面其余内容继续可用。
- 805 行 Diff 首次只渲染 800 行，继续加载后显示完整 805 行。
- 超大或截断 Diff 明确提示限制，不阻塞消息和审批操作。

## 6. 问题三：刷新和新标签页丢失登录状态

### 6.1 实际根因

前端 `initSession()` 曾在刷新完成前把认证初始化标记为完成，并发路由守卫可能看到匿名状态。另一个独立根因是 `/codex/approvals` 同时作为前端页面路径和后端 API 路径，Caddy 对硬刷新请求始终按 API 转发，直接返回 401 JSON。

相关代码：

- 前端认证 Store：`app/stores/auth.ts`
- 路由中间件：`app/middleware`
- 前端路由：`app/types/routes.ts`
- 审批页面：`app/pages/codex/approvals/index.vue`
- Caddy：`E:\python_web_fastapi\work\deploy\caddy\Caddyfile.example`

### 6.2 最佳实践方案

- Access Token 只保存在内存。
- Refresh Token 只保存在 HttpOnly Cookie。
- 每个标签页启动时共享一次初始化 Promise，等待 refresh 和 `/auth/me` 完成后再放行守卫。
- 页面路径与 API 路径永不重叠。审批页面使用 `/codex/approval-center`，API 保持 `/codex/approvals`。
- 部署验收检查 Cookie 的 `Path`、`Domain`、`Secure`、`HttpOnly`、`SameSite` 和代理转发协议。

### 6.3 任务清单

- [x] 认证初始化使用共享 Promise。
- [x] 只在 refresh 完成后设置 `initialized=true`。
- [x] 增加并发初始化只发起一次 refresh 的测试。
- [x] 审批前端路由迁移到 `/codex/approval-center`。
- [x] API 路径保留 `/codex/approvals`。
- [x] 所有导航链接改用新的页面路径常量。
- [ ] 部署流水线增加 Set-Cookie 属性断言。
- [ ] 增加真实浏览器多标签页认证恢复 E2E。
- [ ] 反向代理验收记录 `X-Forwarded-Proto` 与后端感知协议。

### 6.4 验收标准

- 已登录用户硬刷新任务页和审批中心后无需重新输入密码。
- 新标签页直达 `/codex/approval-center` 返回 Nuxt 页面，不返回 API JSON。
- 两个同时启动的路由守卫只触发一次 refresh。

## 7. 问题四：错误响应直接暴露给用户

### 7.1 实际根因

认证 API 的结构化错误曾直接进入 Nuxt 错误页，用户看到 `auth.token.invalid` 和完整 JSON。客户端日志对对象异常只记录为 `Object`，既暴露内部字段又缺少有效诊断上下文。

### 7.2 最佳实践方案

- API 错误先转换为稳定的用户错误模型。
- 401 页面只展示重新登录、返回首页等可执行动作。
- 5xx 展示通用信息，不展示内部堆栈和原始响应。
- request ID 和 trace ID 进入可展开诊断区域。
- 原始异常只进入受控日志系统，并经过敏感字段过滤。

- [x] 5xx 使用通用用户文案。
- [x] request ID、trace ID 保留为诊断字段。
- [x] 对象错误序列化为有意义的消息。
- [x] 普通窗口错误和 Promise 拒绝只记录，不再替换整页。
- [ ] 对接统一前端错误上报平台。
- [ ] 日志上传前增加 token、cookie、Authorization 和绝对路径脱敏。

### 7.4 验收标准

- 用户界面不显示裸 API JSON、堆栈、Access Token 或 Refresh Token。
- 诊断人员仍能通过 request ID 和 trace ID 关联后端日志。

## 9. 问题六：命令审批摘要全部是 unknown

## 10. 问题七：文件审批没有目标路径

- 可通过 `item_id` 与已规范化的时间线 Diff 进行受控关联，但关联结果必须标记来源和可信度。
- 最佳长期方案是扩展 Agent/App Server 协议，使审批请求原生携带稳定文件目标。

## 11. 问题八：审批次数过多且无法分组

### 11.1 实际根因

官方审批协议以单请求为基本单元，现有 API 也只提供单条决策。前端因此逐条展示和提交，普通架构分析中的只读扫描会产生大量交互成本。

2026-08-11 的真实浏览器回归进一步确认：同一 turn 中的 `rg`、`Get-Content`、`git status` 等操作虽然明显为只读扫描，页面仍只显示逐条“允许一次”，没有出现只读组级入口。说明 UI 已具备组级能力，但 Agent 到审批契约的只读分类尚未覆盖真实 Windows PowerShell 包装命令，不能将该能力视为端到端完成。

### 11.2 最佳实践方案

- 展示层按 `thread_id + turn_id` 分组。
- 只读命令组允许用户发起组级确认。
- 后端批量接口返回逐条结果，不假装跨 App Server RPC 实现数据库原子事务。
- 真正的“本轮允许只读命令”应成为有范围、有过期时间、可审计的授权能力，由 Agent 强制执行。
- 长期协议必须由可信执行端返回结构化副作用分类，不能让浏览器解析 shell 字符串决定风险。协议演进前，Agent 只可对经过操作系统 shell 语法解析且完整命中只读 allowlist 的动作标记 `read_only=true`；任何未知、复合写入、重定向、网络或子进程语义都必须降级为逐条审批。
- 写操作、网络访问、额外根目录和权限提升继续单独审批。

## 12. 问题九：审批实时更新存在竞态

### 12.1 实际根因

旧 Store 使用全局 `decidingId`，每次决策后重新加载整个集合。批量点击会相互覆盖提交状态，并与实时 `opened/resolved` 事件竞争，导致按钮突然消失或旧事件回滚新状态。

### 12.2 最佳实践方案

- 每条审批使用稳定 ID 和独立状态。
- Store 依据 `version + updated_at` 判断新旧。
- 决策 HTTP 接受后进入 `acknowledged/claimed`，最终状态由 `approval.resolved` 权威确认。
- 批量能力返回逐条结果，明确部分成功。
- 发生 stream gap 时重新读取权威审批集合。

### 12.3 任务清单

- [x] 使用 `decisionStateById` 和 `decisionErrorById`。
- [x] 禁止同一审批重复并发提交。
- [x] 单条决策后不再全量刷新队列。
- [x] 增加旧版本事件保护。
- [x] 展示最近解决的审批及结果。
- [x] 每条审批错误独立呈现。
- [ ] 批量后端接口返回 `applied/conflict/expired/failed` 逐条结果。
- [ ] stream gap 后自动触发审批权威重载。
- [ ] 增加批量点击、乱序事件和网络重试 E2E。

### 12.4 验收标准

- 同时操作多个审批时，各自按钮和错误互不影响。
- 已解决审批不会被旧 opened 事件恢复为 pending。
- 用户始终能判断审批是提交中、已确认、已过期、冲突还是失败。

## 13. 问题十：任务启动阶段状态互相矛盾

### 13.1 实际根因

顶部状态、消息区提示和 operation 提交状态来自不同字段，导致消息已经提交但顶部仍显示空闲或旧线程状态。

### 13.2 最佳实践方案

- 建立统一派生状态机。
- operation 本地状态负责 `submitting/accepted/starting`。
- thread 和 turn 权威状态负责 `running/terminal`。
- 待审批集合覆盖为 `waiting_approval`。
- 超过活动阈值且没有审批时派生为 `stalled`。

### 13.3 任务清单

- [x] 任务页实现统一 phase selector。
- [x] 消息提交、operation 生命周期、turn 生命周期和审批状态统一参与派生。
- [x] turn 生命周期事件清除 pending operation。
- [x] 所有主要状态区域使用同一个派生值。
- [ ] 将状态机提取为纯函数并补充完整状态转换表测试。
- [ ] 后端公开稳定的 operation phase，减少前端时间推断。

### 13.4 验收标准

- 消息提交后状态按 `submitting -> accepted -> starting -> running` 单向推进。
- 等待审批时所有区域一致显示 waiting approval。
- 终态后不残留运行动画。

## 15. 问题十二：任务长期 active 且无进展

### 15.1 实际根因

现有链路有 Agent 心跳、状态同步和 operation 对账，但缺少 turn 级最后活动时间、租约和 watchdog 终止语义。浏览器只能看到线程仍为 active，无法判断 App Server 正在工作、等待内部资源还是已经失联。

### 15.2 最佳实践方案

- 前端显示当前阶段、最后活动时间和重新同步操作。
- 重新同步读取 Agent 权威快照，不重复执行原命令。

### 15.3 任务清单

- [x] 前端根据最后活动时间显示 stalled 状态。
- [x] 前端显示最后活动时间。
- [x] 提供重新同步，而不是无限动画或自动重试写操作。
- [x] 后端已有 Agent 状态同步和 operation 对账基础能力。
- [ ] 线程/turn 契约增加 `phase` 与 `last_activity_at`。
- [ ] Agent 对活动 turn 发布节流心跳。
- [ ] 控制面建立 fenced turn lease。
- [ ] watchdog 将失效 turn 标记为 `unknown/stalled` 并发布实时事件。
- [ ] 用户确认后才允许对未知写操作重新执行。
- [ ] 增加断网、Agent 重启、App Server 卡死和事件丢失测试。

### 15.4 验收标准

- 超时后用户能看到最后活动时间和重新同步入口。

## 16. 问题十三：返回会话后不会保持最新位置

- 用户主动向上滚动后才关闭 following。

### 16.3 任务清单

### 16.4 验收标准

会话栏、正文和按需上下文栏；项目栏负责主机、项目、搜索、归档和设置，会话栏不再截取前七条，也不再
维护独立“最近任务”。移动端改为 Remote 逐层导航：主机 -> 项目 -> 会话，正文全屏且 Composer 固定在
安全区内，Diff、终端、测试和审批使用上下文页或底部弹层。

### 26.2 会话索引事实源

会话列表来自服务端索引。标题优先级为手工名称、App Server 名称、首条用户消息短标题和
`新会话 · 创建时间`；打开详情不会再通过 sessionStorage 补标题。排序为 `is_pinned DESC`、
`recency_at DESC`、`created_at DESC`、`upstream_thread_id DESC`，`last_synced_at` 只表示同步时间。
未知历史状态显示“状态未知”，真实请求加载 fallback 才显示“同步中”。

### 26.3 组件和资源所有权

`codex-session` 是 host、workspace、conversation 索引和选择的唯一 Store；`codex-approvals` 是待审批和
审批状态的唯一 Store；`codex-ui` 只保存上下文栏模式、移动导航层级、草稿和滚动位置。桌面
`CodexContextPanel` 与手机上下文页共用相同选择模型，审批中心和会话内均复用 `CodexApprovalCard`。
页面卸载、主机切换和退出登录必须清理 WebSocket、timer、弹层滚动锁、临时选择、草稿和测试上下文。

### 26.4 真实回归

`pnpm verify` 通过：31 个 Vitest 文件、167 项测试、覆盖率 Statements 72.37%、Branches 64.83%、
Functions 77.77%、Lines 73.49%，生产构建成功，Playwright 9 项通过。真实生产视口
`1440x900`、`1280x800`、`1024x768`、`820x900`、`360x800`、`390x844`、`430x932` 均无横向溢出、
Composer 遮挡或重复导航；前端生产镜像通过带 env-file、项目名和 Caddy overlay 的 Compose 命令更新，
未删除数据卷。

## 24. 发布观察指标

- 审批页面未捕获异常数。
- `approval.opened` 契约拒绝数。
- 审批旧版本事件丢弃数。
- 审批从 opened 到用户决策的 P50/P95。
- waiting approval 停留时间。
- Diff 规范化失败数与最大渲染行数。
- 页面 fatal 错误率与局部边界错误率。
- Refresh 成功率、单标签并发 refresh 次数和 401 恢复率。
- active turn 无活动超过阈值的数量。
- stream gap 与权威重新同步次数。

## 25. 最终结论

本次治理的核心不是增加更多加载动画，而是让浏览器只消费规范化数据、让实时事件不弱于 REST 权威快照、让审批和任务状态具备明确状态机，并把错误限制在最小可恢复范围。已落地修改解决了审批崩溃、Diff 空值崩溃、认证初始化竞态、页面/API 路径冲突、等待审批不可见、命令摘要 unknown、审批提交状态竞争、元数据退化、平板布局拥挤和日志缺少上下文等直接问题。

文件审批原生目标、后端批量审批、turn 级授权以及 turn lease/watchdog 属于协议和控制面能力，必须按本文 P1 清单继续建设，不能用前端字符串猜测、顺序循环或无限动画替代。
