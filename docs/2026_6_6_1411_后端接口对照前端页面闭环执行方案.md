# 后端接口对照前端页面闭环执行方案

## 任务目标

交付一套基于后端 `E:\python_web_fastapi\work` 真实 FastAPI 接口的 Nuxt + TypeScript 前端页面与功能闭环方案。

完成判定：前端完成认证登录、主页隔离、业务后台、运维控制面、接口强类型调用、权限裁剪、测试与文档回归；后台管理内容不再占用主页，`/` 只保留空白占位并仅显示“首页”。

> 历史状态说明：本文执行结果记录的是 2026-06-06 本地环境闭环，不代表当前发布门禁；当前发布必须重新执行 `pnpm release:check` 并以本轮任务清单记录为准。

## 全局约束

- 本方案基于 2026-06-06 对后端 `src/api/**/route_*.py`、`contract_*.py` 和前端 `app/**` 的源码扫描；若历史文档、图谱、源码冲突，以源码为准，历史文档可能过期。
- 接口契约统一遵循“公共头字段 + 强类型扩展字段”：外层 `ResponseEnvelope.header` 承载 `code/message/request_id/trace_id`，业务数据进入 `data`；admin 子域继续用 `data.header + data.detail`，`detail` 必须按模块强类型建模。
- 前端不得把 admin `detail` 长期保留为 `unknown`；允许 Phase 1 临时过渡，但 Phase 3/4 页面接入前必须补齐字段类型、请求体类型、operation/kind 校验。
- 主页 `/`、通用登录 `/login`、注册状态页 `/register`、业务后台 `/admin/**`、运维控制面 `/admin/ops/**` 必须隔离；业务后台默认只暴露 `admin_identity` 与 `admin_audit`。
- 后端当前未开放公开注册接口；前端注册页只展示真实不可用状态，不伪造提交或临时写入。
- 权限以后端为准：`admin + auth:read/auth:manage` 为业务后台，`admin + system:read/task:dispatch/security:manage` 为运维控制面。
- 请求层继续使用 Bearer token + JSON body：`/auth/token`、`/auth/refresh`、`/auth/revoke` 不自动携带 access token，受保护接口统一注入 `Authorization: Bearer <token>`。
- 页面与组件使用现有布局、Pinia store、`Base*`/`App*` 组件和 `useAuthenticatedApi()`；不引入新的 UI 框架。
- 日志与错误展示必须保留 `request_id/trace_id`，禁止吞掉后端 envelope 中的错误码。

## 验收标准

- `/` 不再承载管理员管理具体功能；匿名访问 `/admin/**` 跳转 `/login?redirect=...`。
- `/login` 是通用登录入口；管理员账号登录后可进入业务后台，普通账号默认回到 `/`。
- `/register` 展示注册暂未开放；未来后端提供公开注册接口后再接入真实提交链路。
- 管理员区不提供单独登录页，只提供退出入口；退出后清理本地会话并回到 `/login`。
- 管理员账号登录后可进入业务后台，按 scope 展示身份管理、业务审计；`/admin` 与 `/admin/**` 均有路径级守卫兜底，运维入口仅在后端挂载对应路由且 `NUXT_PUBLIC_ADMIN_OPS_ENABLED=true` 时展示。
- 身份管理、审计、任务、设置、日志、安全、系统概览接口调用均有强类型契约和对应页面闭环。
- 所有 admin 子信封校验 `kind/schema_version/operation_name/detail`，请求体按对应 command envelope 发送。
- `pnpm format:check`、`pnpm lint`、`pnpm typecheck`、`pnpm test -- --run`、`pnpm test:coverage`、`pnpm build`、`pnpm test:e2e` 通过。

## Phase 2

### 目标

释放主页并建立页面隔离：`/` 是空白占位，`/login` 是通用认证入口，`/register` 是注册状态入口，`/admin` 是后台总览，`/admin/ops` 是运维控制面。

当前阶段完成后，主页不再承担管理员管理；登录/注册使用独立 `auth` 布局，不进入管理员侧栏/顶部栏骨架；管理员区不再有单独登录页，只保留退出入口；业务后台与运维控制面通过路径守卫、route meta、导航和权限统一隔离。

### 依赖

依赖 Phase 1 的权限契约、现有 `auth` store、`framework.global.ts` route middleware、`APP_NAVIGATION_ITEMS`。

### 模拟用法

```ts

```

## Phase 3

当前阶段完成后，管理员可在业务后台查询并维护用户、角色、scope，查询业务审计记录。

### 依赖

### 模拟用法


| --------------------------- | -------------- | ------------------------------------------------------------------------- |
| AdminTaskExecutionRecord    | 任务执行记录   | 查询 `/admin/tasks/executions` 与详情 `/admin/tasks/executions/{task_id}` |
| AdminTaskDispatchEnvelope   | 任务派发信封   | `payload_json` 必须保持字符串，不在前端任意拍平对象                       |
| AdminSettingsReloadEnvelope | 配置热更新信封 | 候选读取与执行结果均校验 `operation_name`                                 |
| AdminLogRecordPayload       | 日志记录       | 支持 level、event_kind、request_id、trace_id、时间区间过滤                |
| AdminSecurityEventPayload   | 安全事件       | `/admin/security-events`，属于日志查询能力                                |
| SecurityIpBlockPayload      | IP 封禁        | `/security/ip-blocks`，不走 admin 子信封，仅走公共 envelope               |
| SystemOverviewAdminPayload  | 系统概览       | `/system/info`，需要 `admin + system:read`                                |
